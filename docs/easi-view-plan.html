Recommended architecture

EASI JS provides the ingestion and normalization boundary. Our frame source supplies original scalar samples and geometry to our WebGL2 engine. Our browser workspace composes the independently implemented viewing, tools, and workflow modules.

EASI JS 1.0.0

Transport and streaming DICOM parsing through the published pipeline APIs. Maintain the independently licensed library boundary.

EASI View frame source and runtime

Normalized raw samples and geometry, lazy worker decoding, request cancellation, encoded input limits and byte-budgeted decoded caches.

Owned rendering engine

Direct WebGL2 scalar textures and shaders, DICOM display transforms, calibrated coordinates and a CPU reference/fallback. Later own MPR and GPU volume rendering.

Owned tools and browser workspace

Framework-free ES-module 2D alpha, viewport interactions, calibrated measurements, cine, import and source lifecycle; later multi-viewport and extension APIs.

Optional server integrations

DICOMweb archives, identity provider, annotation/report persistence and Node DIMSE gateway. Local files remain in the browser.

Zero-footprint: no installed viewer or browser plugin. Local files can remain entirely on the device; archive, enterprise and optional rendering services can run on servers.

  • Zero-footprint means no installed viewer or browser plugin. Browser processing and server-backed archive/integration modes can coexist.
  • Local-file mode parses and displays locally, with no file upload or persistent patient-data storage by default.
  • EASI remains the ingest and normalization boundary through a direct raw-frame source contract.
  • Keep raw scalar samples and physical geometry; display RGBA is a presentation product, not a quantitative volume source.
  • Measure streaming value using time to first useful image, responsiveness, retained bytes, cancellation and buffer disposal.
  • Streaming already exists in other viewers. Differentiate through the expressive pipeline API, a reusable owned engine, resource control and integration experience.
  • Publish a capability matrix by SOP class, transfer syntax, photometric profile, frame model, browser/device and supported operations.
  • Clinical intended use, specialty algorithms and diagnostic measurements need explicit validation criteria separate from a feature checkbox.
  • Own the viewer engine, cache, and tools. Add codec-only providers deliberately; do not add a substantial third-party viewer or rendering framework.
Current EASI JS foundation work to prove before broad viewer claims
  • Current convenience decoders primarily produce display RGBA. Quantitative pixels and volume loading need a raw scalar output contract.
  • Native multiframe detection and encapsulated fragment/frame extraction need broader correctness coverage, including empty/basic/extended offset tables.
  • Enhanced shared/per-frame metadata and exact modality/VOI/presentation behavior need normalized, independently validated support.
  • JPEG2000, JPEG-LS and HTJ2K runtimes require explicit provision, supported-profile validation and licensing notices.
  • Streaming the parser and selecting attributes do not automatically provide a bounded, frame-oriented viewer cache or progressive decoded frames.
  • SEG/SR/PresentationState accessors do not by themselves implement object visualization, editing or interoperable save workflows.

Implementation phases

P1 is a usable 2D alpha. P1 + P2 define the proposed general-viewer 1.0 target. Later phases expand validated capabilities. Phase counts are candidate scope for selected profiles, not a promise to ship every format or specialty immediately.

P016 candidate features

Owned engine and correctness foundation

Technical milestone

Independent repository, matching source-available license, raw-pixel/frame/geometry contract, owned WebGL2 renderer with CPU reference, worker lifecycle, synthetic fixtures and byte-budgeted caches.

Acceptance gate

Independent signedness, High Bit, endian, window, inversion, orientation, spacing and cancellation tests pass; repeated loads dispose CPU/GPU resources; no external viewer engine is present.

P139 candidate features

Professional 2D alpha

0.1 alpha

Local files/folders, study and series organization, one configured DICOMweb archive, thumbnails, stack navigation, cine with declared timing, presets, pan/zoom/rotate/flip, layouts, metadata, keyboard/touch and calibrated basic measurements.

Acceptance gate

An independently encoded CT/MR/X-ray/US corpus works across the selected browser/device matrix. Local viewing is network-free and unsupported inputs fail clearly.

P264 candidate features

Reliable general viewer

1.0 target after P1 + P2

Validated compressed and enhanced profiles, patient-geometry sorting, workers, bounded caches and prefetch, authenticated archive integration, priors, linked views, layout presets, richer ROI tools, persistence and operational hardening.

Acceptance gate

Published compatibility matrix, reproducible performance budgets, quantitative reference checks, repeated-study cleanup, multiple archive implementations and source-appropriate security/access tests all pass.

P314 candidate features

Volume and multimodality workbench

Later core release

Verified volume assembly, axial/coronal/sagittal and oblique MPR, crosshairs, reference lines, slabs, MIP/MinIP/average projections, curved reconstructions, 3D rendering, geometry-aware fusion and selected registration.

Acceptance gate

Known phantoms verify geometry and reformat measurements. Nonuniform, mixed-orientation or nonmatching-frame-of-reference data receives defined handling.

P444 candidate features

Interoperable results and research

Workflow modules

SEG viewing/editing, SR measurement tracking, GSPS/KOS, parametric maps, AI result overlays, quantification, longitudinal research and standards-based export/save.

Acceptance gate

Output objects retain correct image/frame references and units and round-trip through independently implemented viewers and validators. AI display, editing and execution have separate contracts.

P526 candidate features

Deployment/integration modules

Identity and roles, worklists, assignment, hanging-protocol authoring, reporting, EMR/FHIR context, sharing/collaboration, audit, policy controls, deployment operations and optional legacy PACS gateway.

Acceptance gate

Authorization, session cleanup, audit and concurrency are exercised end-to-end in a representative institution integration. Local-only mode remains an explicit supported workflow.

P669 candidate features

Breast/DBT/ABUS, echo/cardiac/vascular, nuclear oncology, RT review, dental/orthopedics, WSI pathology, ophthalmology and advanced research analysis.

The first implementation work package

  1. Create an independent local easi-view repository with matching community licensing and a synthetic-only asset policy.
  2. Keep a focused src/data, src/runtime, src/render, src/ui, test and docs structure; split packages only when a reusable boundary is proven.
  3. Implement a direct raw-frame contract and owned WebGL2 renderer with independent scalar, windowing and geometry expectations.
  4. Prove one viewport using local files and a bounded native DICOMweb multipart response with lazy worker decoding and explicit resource cleanup.
  5. Expand compressed and enhanced support through independently validated providers and additive EASI APIs when needed.
  6. Build archive browsing, multiple viewports and richer tools after the first numerical and lifecycle gates pass.
  7. Use the evidence-linked catalog for further scope decisions; keep actual support recorded in STATUS.md.

Recommended first milestone: EASI-backed CT/MR stacks, calibrated 2D viewing and US cine from local files and one DICOMweb archive, with correct scalar values, cancellation and bounded caches. This proves the foundation that later modules depend on.

Evidence and planning boundaries

  • The catalog is a comprehensive candidate backlog for the named benchmarks, not an exhaustive inventory of every viewer, optional module or future release.
  • Vendor documentation is evidence of advertised capability, not proof of accuracy, interoperability, performance or installation-specific availability.
  • Specialty entries are a menu of potential modules, not a simultaneous first-release commitment.
  • Keep EASI JS and its license/versioning separate from viewer code; preserve third-party runtime licenses and notices.
  • An independent local research alpha starts P0/P1. The broader feature catalog remains a candidate backlog, and publication is a later release task.
